# Sentinel — Codebase Analysis & Improvement Recommendations

*Prepared 2026-07-05 against `main` @ `903c7e3`. Every finding below was verified against the actual code (file:line cites throughout), and each recommendation was adversarially checked so that nothing proposed here already exists in the repo. The two headline defects (D1, D2) were reproduced directly.*

---

## 1. What the application is

**Sentinel** is a pre-launch internal **employer-monitoring, compliance, and business-intelligence platform** for Vision Freights LLC (freight/logistics). It ingests organizational activity from company-owned **Google Workspace** (Gmail, Drive, Directory — Calendar planned) and **PayPal**, normalizes it into append-only Postgres event tables, runs a two-stage detection pipeline (deterministic DLP pre-filter → Claude adjudication), computes SLA/productivity metrics and transparent per-employee/department risk scores, raises deduplicated alerts dispatched via email + WhatsApp + a realtime in-app feed, and produces Claude-written executive reports.

- **Stack:** Supabase Postgres (RLS, pg_cron, pg_net, Vault, Realtime) + 9 Deno Edge Functions; React/Vite/Tailwind/Recharts dashboard; Anthropic Claude tiered by cost (Haiku classification → Sonnet summaries → Opus reports).
- **Compliance-by-design posture:** content-class row gating, default-deny RLS, an append-only "audit-of-the-watchers" log, go-live gates (`monitoring_active` / `notice_delivered`, default **off**), data minimization (bodies retained only when a policy flags a message), retention TTLs, and a compliance doc pack (monitoring notice, DPIA checklist, DSAR runbook, jurisdiction config).

### What is genuinely well built

- **The schema is ahead of the code.** The 24-table model anticipates almost every roadmap feature (content_class gating, dedup keys, per-factor risk breakdowns, report scopes, audit actions). The majority of recommendations below are *"connect existing schema to code,"* not redesign.
- **The compliance gates are real, not decorative.** `ingest-email` and `sync-directory` verifiably refuse to collect org-wide data until `monitoring_active` is set (`ingest-email/index.ts:116`, `sync-directory/index.ts:11`), and `analyze` scrubs non-flagged bodies (`analyze/index.ts:107-109`).
- **The audit log is append-only even against the service role** — `BEFORE UPDATE/DELETE` triggers raise, and triggers bind the RLS-bypassing service role (`0001_init_schema.sql:439-449`).
- **The cost-tiered AI architecture is sound:** deterministic pre-filter → cheap Haiku adjudication → Opus only for narratives, with refusal handling and a deterministic fallback.
- **The connector abstraction works:** a single `SourceConnector` + `NormalizedRecord` DTO shape makes dev (`mcp` single-account) vs. production (`google_admin` org-wide) a config change, not a rewrite.
- **Risk scoring is transparent by design** — a linear weighted model with a per-factor breakdown JSON and CEO-tunable weights, deliberately *not* an LLM.
- **CI exists** — web build + typecheck and three Deno unit-test suites on every push/PR.

## 2. Verified defects — fix before anything else

These are confirmed bugs (each line-verified; D1 and D2 reproduced), roughly in order of blast radius. Several are launch-blockers: they break the moment real employee data flows.

**Compliance representations that are currently untrue in code** (what the docs/schema promise vs. what the code does):

- `employees.is_monitored` — documented as the per-person kill switch *and* the DSAR erasure remedy (`dsar-runbook.md:32`) — is **read by nothing**; opted-out employees keep being monitored, so the erasure remedy is a no-op.
- `ingest-drive` has **no `monitoring_active` gate** (unlike `ingest-email`) — it would collect real sharing data pre-go-live the moment a drive source is flipped to `google_admin` (`ingest-drive/index.ts:15-22`).
- `body_ref` is documented as a "pointer to encrypted blob" (`0001:145`) and the DPIA lists encryption as the breach mitigation — it stores **raw plaintext inline** (`ingest-email/index.ts:83`).
- Per-jurisdiction retention overrides taught by `jurisdiction-config.md` are **silently ignored** — the purge reads only `jurisdiction IS NULL` rows (`0003_cron.sql:35-36`). The purge also covers only 2 of ~10 data-holding tables, and `sent_at IS NULL` rows are immortal.
- The UI tells content-role users *"revealing message content is logged"* (`Security.tsx:37`), but **nothing logs human content access** — only machine reads are audited (`analyze/index.ts:78`). ceo/admin can `SELECT body_ref` directly under RLS with no audit row.
- `sync_state` has RLS enabled with **zero policies** — connector health is invisible to every role, while the runbook tells operators to check exactly that data.

## 3. Recommendations

Organized by theme. Effort is **S / M / L**; impact is the second tag. Each item was verified as *not already implemented* and *factually grounded*. Items that also fix a defect above are cross-referenced.

### A. Detection & feature coverage

The `alert_type` enum defines 11 types but only 7 have emitters, and several schema features are fully modeled yet dead. Wiring them up is high-leverage because the pipeline they feed (`raiseAlert` → dedup → dispatch → risk factor) already exists.

1. **Competitor-contact intelligence** *(S, high)*. `identities.is_competitor` (`0001:78`) is never written or read, and the seeded `competitor_contact=2.5` risk weight has no `TYPE_TO_FACTOR` mapping — so it sits permanently at zero *while inflating the risk denominator* (~14% of the scale is unreachable). Add a Settings editor for competitor domains, a post-DLP scan in `analyze` for outbound mail to competitor identities, the factor mapping, and a critical escalation when the same email also carried a DLP hit. For a freight company, "salesperson emails the rate sheet to a rival forwarder" is *the* nightmare scenario — today Sentinel detects **what** leaked but not **who** it went to.
2. **Drive/download activity + mass-export burst detection** *(M, high)*. `file_events` (with `downloaded`/`exported` actions), the `NormalizedFileEvent` DTO, the `driveActivity`/`adminReports` OAuth scopes, and the seeded `mass_export=2.5` weight all exist with **zero writers**. Build an Admin SDK Reports connector (`applicationName=drive`), an `ingest-files` function + cron, and a burst detector (>N downloads/hour → `anomaly` alert, then map `anomaly`→`mass_export`). An employee downloading 500 files currently triggers nothing.
3. **Departing-employee risk mode + watchlists** *(M, high)*. `employment_status='terminated'` is never written — `sync-directory` only maps suspended→inactive and never diffs the roster, so deleted accounts freeze at last-known status. Add roster diffing, a watchlist (`watch_until` / `watch_reason`), a configurable risk multiplier for watchlisted users, evidence retention (skip the body-scrub for them), high→critical dispatch escalation, and a 30-day look-back sweep on transition to terminated/watchlisted. The two weeks around resignation are the classic exfiltration window; in freight, the leaver takes the customer book. *(Every insider-risk buyer asks for this scenario first.)*
4. **Attachment sha256 fingerprinting** *(M, high)*. `attachments.sha256` is always null, `attachments_sha256_idx` is unused, and `dlp_match_type='fingerprint'` silently falls through to regex (`engine.ts:50`). Hash sensitive-typed attachments (`crypto.subtle` over `messages.attachments.get`), add a `sensitive_documents` registry table + Settings UI, and implement `fingerprint` as an exact hash lookup. Keyword DLP on freight rate sheets is inherently noisy ("rate" is in every email); a fingerprint of *the* master rate card is a zero-false-positive detector and a strong demo differentiator.
5. **SLA engine v2** *(M, high)*. `compute-metrics` uses only `first_response` rules — the seeded `followup`, `quotation_turnaround`, and `ops_milestone` rules are loaded and discarded (`compute-metrics/index.ts:19`), and there is no business-hours math (a 6 pm enquiry answered at 9 am reads as a 900-min breach). Add a shared `businessMinutesBetween()` helper (the `business_hours` policy exists: Asia/Dubai 08:00–18:00, workdays), implement the three ignored rule types, and require external-inbound / internal-outbound pairing. Quotation turnaround is *the* freight-forwarding KPI, and it is already seeded config.
6. **Login-anomaly detection** *(M, medium)*. `login_anomaly` is the last emitter-less alert type; it is already mapped to the `offhours_anomaly` risk factor, `SCOPES.adminReports` is declared but unused, and the runbook already authorizes the scope. Pull Admin Reports login events for failed-login bursts, off-hours logins, and first-seen IP/country. Account **compromise** (as opposed to insider action) is currently a total blind spot.
7. **Calendar connector** *(M, medium)*. The last missing source: the table, DTO, `calendarReadonly` scope, a seeded active `calendar` source, and an RLS read policy all exist, and the README even advertises `ingest-calendar/`. It is the fourth copy of an established connector+ingest pattern, and it enables the "met the competitor, emailed the rate sheet the next day" correlation.
8. **Alert case management** *(M, high)*. Triage today is three status-only buttons; `acknowledged_by`/`resolved_by` (which exist) are never populated, and `evidence_json`/`source_event_*` are never rendered. Add an `/alerts/:id` route with the evidence panel and a resolved link to the source row, an `alert_notes` table + `assigned_to` column, real acknowledged/resolved attribution, and an audited "reveal content" action (see D3 below). *This is the single biggest gap between Sentinel and a Purview-class product for its primary daily user — the security analyst.*

### B. Robustness, architecture & operations

1. **Fix D1 + D8** *(S, high)*: correct the destructure; add `unique(identity_id, rule_type, destination)` on `forwarding_rules` and `unique(source_id, provider_file_id, grantee)` on `file_permissions`; convert the inserts to upserts with a `last_seen_at` bump; and gate `ingest-drive` on `monitoring_active`.
2. **Real org-wide incremental Gmail sync** *(L, high)*: fixes D4. Inject the roster (employees where `is_monitored` and active) via a new `ConnectorContext.users`; loop `messages.list` pages until exhausted (honoring the never-used `PullResult.done`); keep a per-user `{ts, pageToken}` cursor map in `sync_state.cursor`; upgrade to `history.list`/historyId later. Every downstream layer is only as good as this feed.
3. **Authenticate the functions** *(S, high)*: fixes D3. A shared-secret header check in a tiny `_shared/authz.ts` wrapped around all 9 handlers; the secret lives in Vault and is sent by `app_invoke_function`; plus `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` on the two `SECURITY DEFINER` helpers.
4. **Pipeline observability** *(M, high)*: a `job_runs` table (function, started/finished, status, records, alerts, claude_calls, error) + a `withRun()` wrapper used by all entrypoints; replace the silent catches (`gmail.ts:150,158`, `paypal.ts:51,56`, all three Claude helpers) with `console.error` + counters; set the schema-anticipated-but-never-used `'throttled'` status on 429/403; and add a `sync_state` SELECT policy so a health UI can exist. *A monitoring product whose own monitoring is fire-and-forget will fail its first week silently.*
5. **Atomic alert dedup + a real dispatch state machine** *(M, high)*: fixes D6. Replace check-then-insert with one `INSERT ... ON CONFLICT (dedup_key) DO UPDATE SET occurrence_count = occurrence_count + 1` RPC; move dispatch bookkeeping out of `evidence_json` into `dispatch_status` / `dispatch_attempts` / `dispatched_at` columns; only mark sent on actual channel success; retry with an attempt cap on subsequent 5-min ticks; wrap `sendWhatsApp` in try/catch.
6. **Harden the Claude wrapper** *(M, medium)*: fixes D5's cost half. Explicit per-call timeouts (~30 s for classify; longer for the streamed Opus report) and an explicit `maxRetries`; a per-run adjudication budget via `getPolicy('claude_max_calls_per_run')`, processing highest severity first; an `ai_calls` ledger (fn, tier, model, latency, tokens from `res.usage`, outcome); record negative verdicts so non-disclosing emails aren't re-adjudicated ~144×/day; typed error handling (`Anthropic.RateLimitError` → `APIConnectionError` → base `APIError`).
7. **Migration/seed idempotency + schema invariants** *(M, medium)*: fixes D7. `UNIQUE NULLS NOT DISTINCT` (PG15+) on `policies`; natural keys `dlp_rules(name)` and `sla_rules(department_id, rule_type)`; a `CHECK ((content_class='content') = (body_ref IS NOT NULL))` on `email_events` (all writers already maintain it by convention — this makes the central privacy promise auditor-verifiable); and the missing hot-path indexes: `attachments(email_event_id)` (queried per-email inside a 500-email loop), `alerts(employee_id)`, a partial `finance_events(object_type, due_at) WHERE paid_at IS NULL`, `file_permissions(detected_at)`, and `audit_log(occurred_at)`.
8. **Complete the retention purge** *(M, medium)*: extend beyond `email_events`/`file_permissions` to `forwarding_rules`, orphaned `email_threads`, `finance_events`, resolved `alerts`, `metrics_daily`, `risk_scores`, aged `reports`, and `cron.job_run_details` (which grows unboundedly under 11 jobs); a created-at fallback for null `sent_at`; jurisdiction-aware TTL resolution via `employees.jurisdiction`; and a proper `retention_purge` audit action recording per-table row counts instead of the mislabeled `run_query`.
9. **Housekeeping** *(S, low)*: `packages/shared` is dead code — no zod (despite the README's "zod schemas" claim) and no consumers (apps/web redefines its own types; the Deno functions can't import it as-is). Either make it real (zod schemas checked against the SQL enums, consumed by web via the workspace and by Deno via an import map) or drop the claim. Add a **deploy** pipeline — CI tests but nothing deploys migrations/functions, so environments will drift.

### C. Reporting & analytics *(explicitly requested focus)*

Today: one org-scope Opus narrative (daily 06:00 / weekly Mon 06:30) stored in a table and rendered as raw `<pre>` text. `recommendations_json`, `pdf_ref`, four of the seven documented report types, monthly scheduling, and any *delivery* are all missing. Build-out, cheapest first:

1. **Deliver the reports** *(S, high)*. Extract `sendEmail()` from `alert-dispatch` into `_shared/notify.ts`; email the narrative to `ALERT_EMAIL_TO` after insert; add the missing monthly cron (`0 7 1 * *` — the handler already supports `monthly`). Fix the confident-empty failure mode: query errors currently collapse to empty arrays (`report-generate/index.ts:28-33`), producing a plausible Opus "all clear" marked `final` — mark degraded input as `draft` and skip the email. *This is the single cheapest step from "reports exist in a table" to "the CEO gets a briefing every morning."*
2. **Structured recommendations + rendered Markdown + drill-through** *(M, high)*. Request the report as structured output (`{narrative_md, recommendations:[{priority,title,rationale,related_alert_ids}]}` — the `json_schema` machinery already exists in `classify()`, and it composes with streaming + adaptive thinking on Opus); include alert ids in the digest so recommendations can cite them; store `recommendations_json`; render Markdown (not `<pre>`) with recommendation cards linking to the Security page filtered to those alerts. An executive reading "investigate 3 DLP incidents in Sales" currently has no path to those incidents.
3. **Scoped report types** *(M, high)*. Implement the `dept` / `employee` / `security` / `risk` types the schema comment documents (`0001:356`): accept `{type, scope_type, scope_id, days}`, filter the three feeds, write the scope on the row, and add a dept-scoped RLS policy on `reports` (dept_manager currently can't read reports **at all**). "How is Ops doing vs. Sales" is the CEO's first real question.
4. **Monthly compliance report** *(M, high)*. A `security`-type digest built from governance tables rather than operational ones: `audit_log` grouped by action/actor (content accesses, retention-purge confirmations), alert-triage throughput and false-positive rate per type, and policy/DLP-rule changes. **Prerequisite the schema doesn't yet capture:** policy and rule changes are logged nowhere (`change_policy` and `logSystemAction` have zero callers), so add `AFTER UPDATE` audit triggers on `policies`/`dlp_rules` first. This turns the "audit-of-the-watchers" pitch into a standing, defensible artifact for counsel and for monitored employees.
5. **Department & org rollups in `metrics_daily`** *(M, high)*. `compute-metrics` writes only `scope_type='employee'` rows and drops the `unassigned` accumulator, so every dashboard recomputes aggregates client-side from capped employee rows. Add a rollup pass (department sums + a message-count-weighted avg response, plus org totals). **Correctness note:** org rows can't be upserted with `scope_id = NULL` against the current unique key (NULLs are distinct → duplicate rows every hour) — use a sentinel UUID or a `NULLS NOT DISTINCT` unique index. Then fix `Sla.tsx`, which pulls 300 arbitrary newest rows with no scope/date filter and will **triple-count** once dept/org rows exist.
6. **SLA compliance scorecard** *(M, medium)*. The breach pass/fail is already computed and then discarded; persist `sla_within_count` / `sla_breach_count` / `sla_compliance_rate` per employee and department (with the business-hours clamp from A5, so overnight enquiries stop reading as breaches), and surface a per-department scorecard + compliance-rate trend on `Sla.tsx`. This is the one-line "are we meeting our SLA" number a freight CEO actually wants.
7. **Finance AR aging report** *(S, medium)*. `finance_events` already carries `amount`/`currency`/`due_at`/`paid_at`/`counterparty`, but `Finance.tsx` shows only row **counts**. Add aging buckets (current / 1-30 / 31-60 / 61-90 / 90+) with currency-grouped sums, a top-debtors table, and org-scope metric keys (`ar_outstanding_total`, `ar_overdue_total`, `invoices_overdue_count`) that flow automatically into the report digest. Overdue receivables are a first-class freight BI concern and all the data is already in the table.
8. **CSV export, audit-logged** *(S, medium)*. There is no export anywhere and every list is hard-capped. Add an `exportCsv` helper + Export buttons on Security/Sla/Finance/Employees/Reports, each writing an `audit_log` row via the unused `export_report` action and the already-present client `audit_insert` RLS policy. Closes a DSAR-runbook promise at very low cost.
9. **PDF export to Storage** *(L, medium — ambitious)*. Populate the stubbed `pdf_ref`: render `narrative_md` to a branded HTML template (branding driven by a `report_branding` policy row, not the hardcoded "Vision Freights LLC" string), convert with a pure-JS/WASM PDF lib (headless Chromium is unavailable in Edge Functions), upload to a private `reports` bucket, and add a signed-URL Download button. "Monthly PDF in the CEO's inbox" is the tangible deliverable this platform was bought for; an acceptable fallback is print-styled HTML.

### D. Security & compliance hardening

1. **Lock down the unauthenticated surface** *(S, high)* — same fix as B3 (D3). This is the single cheapest, highest-value pre-launch security fix.
2. **Enforce the collection gates the docs promise** *(M, high)*. Make `is_monitored` real (exclude opted-out employees from the roster *and* force `content_class='metadata'` for their events); add the `monitoring_active` gate to `ingest-drive`; honor `store_all_bodies` at *fetch* time so bodies aren't fetched-then-scrubbed (raw content still transits and is stored for up to 10 minutes today). These are the three places where the software-enforced go-live/minimization story is contradicted by code.
3. **Audited, justification-gated content reveal for humans** *(M, high)*. Because RLS grants ceo/admin raw `SELECT` on `body_ref`, no UI discipline can fix the unaudited-read gap — it needs a column-privilege change: `REVOKE SELECT ON email_events FROM authenticated`, then `GRANT` the explicit non-body columns, and route body access through a `SECURITY DEFINER` RPC `app_reveal_content(event_id, justification)` that checks the role, requires a justification, writes the `view_content` audit row, and returns the body. This breaks nothing (apps/web never queries `email_events` directly today) and finally makes "watch the watchers" true for humans, not just for the `analyze` function. Pairs with the UI modal in E2 and the case-management route in A8.
4. **Make `body_ref` a real encrypted blob** *(M, medium)*. As the schema comment and DPIA already claim. Encrypt on write (pgsodium with a Vault key, or a private Storage object), decrypt server-side inside `analyze` *before* the deterministic `scanDlp` pass (rules can match on body, so decrypting only at the Claude-escalation point would silently regress detection), and decrypt inside the reveal RPC so the key never reaches the client. Only three code sites touch the column now; migrating a table full of plaintext later is much harder.
5. **Strip PII from dispatch + fix the delivery bug** *(S, medium)* — D10 + D6's dispatch half. Push a minimal envelope (type, severity, department, count, dashboard deep-link) with an `alert_channel_verbosity` policy; email can stay richer than WhatsApp. WhatsApp via Meta Graph is effectively an unminimized sub-processor.
6. **Per-jurisdiction retention** *(M, high)* — the compliance-critical half of B8. The documented per-region override mechanism (`jurisdiction-config.md`) is currently a no-op; an operator who follows it believes EU data is deleted at 30 days when it lives 365.
7. **DSAR export/erasure as tooling** *(M, medium)*. Turn the runbook's copy-paste SQL into two audited `SECURITY DEFINER` functions — `app_dsar_export(employee_id)` (covering the ~11 subject-data tables the manual SQL misses) and `app_dsar_erase(employee_id)` — behind an admin-only "Compliance" UI card. This is the *only* way to make erasure possible without service-role SQL (RLS is default-deny with no write policies on `employees`/`email_events`), and demonstrable DSAR tooling is a strong sales/defensibility artifact. Monitored employees are the most motivated requesters.
8. **RLS reconciliation migration** *(S, medium)*. Fix verified asymmetries: `viewer` and `dept_manager` currently get **unscoped** SELECT over every employee's per-employee metrics and risk scores (contradicting the "aggregates only" comment); `dept_manager` can read dept alerts/emails but not the threads, attachments, or reports needed to triage, and can't ack/resolve them; `sync_state` is invisible to all roles. Ship with a pgTAP/Deno test asserting the role×table matrix so it stops drifting.
9. **Audited role administration + access review** *(M, medium)*. Operators are provisioned by pasting commented SQL with a hardcoded email, leaving no audit trail of who granted whom what. Add `app_grant_role` / `app_revoke_role` RPCs (last-ceo guard, audited), a minimal Users admin UI, and a quarterly access-review artifact from `audit_log`. For a monitoring platform, *who can watch* is as sensitive as *what is watched*.

### E. UX & dashboard

The dashboard is a clean scaffold, but several pages are thin, two have verifiably wrong query semantics, and data the schema holds has no UI.

1. **Alert triage workbench** *(M, high)*. Turn `Security.tsx` from a flat 100-row table into a triage surface: a row-click evidence drawer (rendering the `evidence_json`, occurrence counts, first/last-seen, and source pointers the UI already fetches but discards), status/severity/type filter chips + search, checkbox bulk ack/resolve, optimistic updates, and an `AlertFeed` realtime subscription extended to `UPDATE`s. The highest-leverage page for the analyst persona.
2. **Content-reveal modal that writes `audit_log`** *(M, high)*. The UI counterpart to D3: a "Reveal source email" action gated to ceo/admin that requires a free-text justification, writes the audit row via the client `audit_insert` policy, then calls the reveal RPC. Today `canSeeContent` only changes a sentence of copy.
3. **Connector health + go-live checklist page** *(M, high)*. A `/system` route: one card per source joined to `sync_state` (mode, `is_active`, `last_run_at` with a staleness badge, `last_status`, `error_detail`) plus a go-live checklist reading the three gate policies. Needs the `sync_state` SELECT policy from B4. "Is it even collecting?" is the first question an admin will ask, and today it requires `psql`.
4. **Tri-state query handling + mutation failure toasts** *(S, high)*. Every route destructures only `data` and renders the empty-state both in-flight and forever on failure — so a broken query or expired JWT reads as "No alerts." Add a `{data, error, loading}` hook (or adopt react-query), skeletons, a distinct error panel, and toasts on mutation failure (check the returned `error` *and* affected-row count, since RLS-filtered updates return `error:null`). The cheapest trust fix in the codebase, and it unblocks every other UX item. *(Note: RLS-denied reads are silently filtered, not errored — the error panel can't claim to detect read denials.)*
5. **DLP rule editor with a live pattern tester + the 5 unexposed policy editors** *(M, high)*. Settings exposes only an `is_active` toggle and 3 boolean gates; `cfg_write` is already `FOR ALL` for ceo/admin, so a full create/edit/delete form needs only new mutations. A client-side pattern tester using the engine's exact semantics would immediately expose the `(?i)` dead-rule bug (D2). Also add editors for `content_retention_days`, `metadata_retention_days`, `internal_domains`, `personal_email_domains`, and `business_hours` — compliance-critical values currently editable only in the database.
6. **Exposure page** *(M, medium)*. A `/exposure` route with two browsers over tables that have writers but no UI: external `file_permissions` (grouped by file, filterable by public-link/grantee domain) and `forwarding_rules`, each linking to its derived alert. Exfiltration via Drive shares and silent auto-forwarding are two of the three headline detections, yet the UI shows only the derived alert title.
7. **Time-series charts + fix SLA/Productivity query semantics** *(M, medium)*. Recharts is a dependency used for one bar chart while both dated series go unplotted. Add a risk-score-over-time line on `EmployeeDetail` (it fetches only the latest score today), a date picker on `Productivity` (its UTC "today" filter renders blank for an Asia/Dubai business until ~04:00 local), and bound the `Sla` query by scope + date window.
8. **Reports: render Markdown, generate on demand, download** *(S, medium)*. Replace the `<pre>` with real Markdown; add a role-gated "Generate report" button calling `functions.invoke('report-generate', {body:{type}})`; add a `.md` download as the interim answer to the stubbed `pdf_ref`.
9. **Role-aware navigation + route guards + department filter** *(S, medium)*. RBAC exists in three layers but the frontend only disables buttons, so a `viewer` or `dept_manager` sees a dashboard full of silently-empty RLS-denied panels. Add `RequireRole` guards, hide nav items by role, and add a department dropdown (the `departments` table has zero UI today) to the alert views.

### F. AI / Claude-powered intelligence

1. **Resurrect the dead regex rules** *(S, high)* — D2. Strip a leading `(?i)`, compile once per rule with the `i` flag, and on compile failure record the rule as broken (audit row / flag `is_active`) instead of silently skipping. Share a pattern-lint between the engine and the Settings write path so future CEO-authored rules can't ship broken.
2. **Prompt-injection hardening** *(S, high)* — D9. Fence employee-authored fields in explicit `<untrusted>` delimiters and extend `DLP_SYSTEM` to say the fenced content is data from a potentially adversarial author and that classifier-targeting text is itself an evasion signal. Apply the same framing to the `report-generate` digest (the employee-controlled text reaching Opus today is file names interpolated into share/exfil alert titles) so it stays safe as the digest grows.
3. **Fail-safe adjudication** *(M, high)* — D5. Cap severity and tag `evidence_json.adjudication='unavailable'` on classify failure instead of fail-open; actually *use* `verdict.confidence` against a `dlp_confidence_min` policy and store confidence/model/rationale in `evidence_json` for the triage UI; typed error handling; a per-run budget; and an `ai_calls` ledger.
4. **Golden-set eval harness for DLP + adjudication quality** *(M, high)*. A labeled JSONL fixture set (~150 synthetic freight emails: genuine disclosures, benign chatter mentioning "contract"/"invoice", personal-account sends, and injection attempts) with a deterministic CI mode (per-rule precision/recall — which would have caught D2) and an opt-in live mode scoring adjudication accuracy and confidence calibration. Regression-tests every edit to `DLP_SYSTEM` or the rules before deploy.
5. **Persist all DLP matches + close the false-positive loop** *(M, high)*. `analyze` keeps only the top-severity match and discards co-occurring hits, and triage outcomes never flow back to the rules. Add a `dlp_matches` table (every hit), a nightly job rolling `alerts.rule_id × status` into per-rule fired/confirmed/FP-rate stats shown beside each rule in Settings, and inject recent false-positive exemplars into the `classify()` prompt as negative examples. Persisting candidates is also what makes precision/recall measurable before tuning.
6. **Wire the dead `summarize()` into anomaly narratives** *(S, medium)*. `score-risk` raises critical `insider_threat` alerts whose summary is just "Composite risk 62/100," and dispatch sends only title+summary — so the 2 am page is uninformative. Call the exported-but-unused Sonnet `summarize()` on high/critical alerts (input: the component breakdown + recent-vs-baseline factor counts already computed) to produce a 2-3 sentence "what changed and why," and fill the empty department `component_breakdown_json`.
7. **Cost-correct the tiering** *(M, medium)*. Two fixes in the Claude wrapper: (a) the `cache_control` marker on the ~80-token system block likely can't achieve a cache hit given Haiku's minimum cacheable-prefix, and the comment claiming the "rule catalog" is cached is false (the matched rule goes into the *uncached* per-item content) — either grow the system block into a genuinely cacheable asset (full active-rule catalog + few-shot negatives) or drop the marker/comment; (b) when a run's flagged candidates exceed a threshold, submit them via the Message Batches API (≈50% cost, `custom_id = email_event_id`) and collect on the next tick, keeping the synchronous path for low volume. *(Verify the exact cache-prefix threshold against current Anthropic docs before implementing.)*
8. **"Ask Sentinel" — role-scoped natural-language Q&A** *(L, high — ambitious)*. A new `ask-sentinel` function — the one function that *should* have `verify_jwt=true` — that builds a user-scoped client from the caller's JWT so existing RLS governs what the model can see, runs a Sonnet tool-use loop over 4-5 strict parameterized read tools (no raw SQL), answers with cited rows, and logs every question via the currently call-site-less `logSystemAction('run_query')` and the `ai_calls` ledger.

## 4. Suggested sequencing

A pre-launch product should spend its next cycles in this order. The theme letters/numbers reference §3.

**Milestone 0 — Stop the bleeding (days, mostly S).** The launch-blockers and the cheapest trust fixes: **D1/D8** (B1), **D2** (F1), **D3** (B3/D1), **D7** (B7), fail-open + PII on dispatch (**D5/D10** → F3, D5), tri-state query handling (E4). None of these add features; they make the platform not silently break or leak on day one.

**Milestone 1 — Make the core loop trustworthy (M).** Real org-wide Gmail sync (B2), pipeline observability + connector-health page (B4 + E3), atomic dedup + dispatch retries (B5), the alert triage workbench + audited content reveal (A8 + E1/E2 + D3), and the eval harness (F4). After this, the daily analyst workflow actually works and you can see whether the monitor is running.

**Milestone 2 — Deliver the promised value (M).** Report delivery + structured recommendations + rendered Markdown (C1-C2), scoped report types + dept/org rollups (C3 + C5), SLA engine v2 + scorecard (A5 + C6), and the collection-gate/retention/DSAR compliance work (D2/D6/D7). This is the milestone where the CEO gets a morning briefing and the compliance pack becomes true-in-code.

**Milestone 3 — Differentiate (M-L).** Competitor-contact intelligence (A1), departing-employee mode (A3), Drive/download + mass-export (A2), attachment fingerprinting (A4), login-anomaly + calendar (A6-A7), the FP feedback loop (F5), encrypted bodies (D4), and — if the appetite is there — "Ask Sentinel" (F8) and PDF export (C9).
